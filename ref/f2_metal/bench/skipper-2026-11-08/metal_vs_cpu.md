# Metal と CPU の比較（2026-11-08）

- 機械: Apple M3 Ultra（32コア、512 GB）。CPU の台帳で占有し、GPU を使うほかの作業は止めてもらって測った（GPU の使用率は測定前に 0〜13%）。
- SKIPPER: main 9c432c7（f32 対応）＋ `benchmarks/bench_scaling.py --repeat 2`。各条件を2回実行して速い方を採用した。
  - Metal の1回目には JIT コンパイルが含まれる。n=16 で +0.1〜0.2 秒、n=26 では差はほぼない（`run_s_all`）。
- 問題: ランダムな横磁場 Ising 鎖（項の数 3n−1）。測ったのは次の4つ。
  - QPE：Trotter の U、m=6。U を63回呼ぶ。
  - ウォーク QPE：m=6。matvec 32回。
  - QSVT：d=9。matvec 5回。
  - LCU：matvec 1回。
- バックエンド:
  - `cpu-f64` / `cpu-f32`: PyPI の scaluq 0.2.0（OpenMP）。24スレッド。`-t8` が付いたものは8スレッド。scaluq の拡張 API は入っていない。
  - `metal-f32`: scaluq の統合ブランチ db94d63b の Metal 版 wheel（AdaptiveCpp と Kokkos SYCL）。拡張 API（C1/C5/B1/B2/D1）を使う。
  - `metal-f32-noext`: 同じ wheel で `SKIPPER_SCALUQ_EXT=0` にしたもの。CPU と同じ API の経路になる。
- 生データ: `metal_vs_cpu.jsonl`（`backend` 列がバックエンド）。

## 読み取れること

- Metal は n≥16 で、CPU の最速の設定より 2〜7 倍速い。いまの f64 の CPU（最速の設定）と比べると 2.3〜9.8 倍速い。
  - 例外は LCU の n≤20 で、matvec が1回だけなので時間が短く、CPU と同程度だった。
- 同じ API の経路（拡張なし）でそろえても、Metal は n≥24 で約2倍速い。差の残りは拡張 API（C5 の Pauli 項をまとめた作用など）による。拡張 API は Metal でも効いていて、matvec の多い計算で 1.7〜1.8 倍になる。
- QPE（Trotter 回路でゲートの数が多い）は拡張 API の影響を受けず、Metal が 2.2〜4.7 倍速い。事前の情報では起動遅延が大きいはずだったが、n=16 でもすでに Metal が速かった。
- CPU の f32 は、f64 に比べて 1.1〜1.8 倍しか速くならない（n≥24 で 24 スレッドのとき）。n≤20 では 8 スレッドのほうが 24 スレッドより速い。
- **CPU f32 の 8 スレッドで、n=26 の QPE とウォーク QPE を SKIPPER が拒否した。**
  - 入力状態のノルム² が 1.0000447 になり、許容誤差 3e-5 を超えたため（`NumericalCheckFailed`）。
  - 原因は scaluq の既知の問題 #472 で、OpenMP の f32 のノルムを各スレッドが float で順に足すため、1スレッドあたりの要素数が多いと誤差が大きくなる。24 スレッドでは 1スレッドあたりの要素数が少ないので通った。
  - Metal は木の形で足し合わせる reduce なので、この問題は出ない。
  - SKIPPER の検査が想定どおり働いて、誤った結果を返さずに止めた例である。
- 結果が正しいことは、`tests/test_precision.py` で別に確かめている（Metal で 12/12 件成功、誤差は 1e-7 程度）。
